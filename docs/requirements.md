> 1. **产品定位更明确：把手工填表变成线上录入**，即"在线文档的增强版"，**不是**带审批与流程管控的业务系统。

> 6. **交付范围收缩为后端**：业务方只负责后端，前端仅需保留接口契约与数据模型。

> **字段命名约定**：本文档为便于阅读使用 `snake_case`（如 `sample_raw`、`form_no`、`sequence_no`）；
> 设计文档 §4 的 Prisma 模型使用 `camelCase`（`sampleRaw`、`formNo`、`sequenceNo`）。**同一字段，仅命名风格不同**，无第二套字段。

## 1. 背景与目标

### 1.1 背景
镜片（含 KF / EVT 相关产品部件）在加硬等工序后需要进行表面质量检验，目前使用纸质表单《镜片表面质量检验记录表》逐批手写记录，存在以下问题：

- 纸质记录难以查询、统计与追溯（按批次、部件号、检验人、日期检索几乎不可行）。
- 手写内容不规范（如"一次加硬"被写在没有栏目名的空格里），无法结构化汇总。
- 不良分类（点伤 / 划伤 / 脏污 / 加硬点 / 垃圾点 × 凹面 / 凸面 / 双面）数据无法沉淀为质量分析依据。

### 1.2 目标
将纸质表单线上化，形成**可录入、可校验、可检索、可统计、可追溯**的检验记录系统。产品定位是**"在线文档的增强版"**——把手工填表变成线上录入，而不是引入审批与流程管控的业务系统：

1. 线上填报表单，**字段与纸质表单一一对应，不遗漏任何一个既有栏目**，不改变现场检验人员的判定口径。
2. 样品信息支持"原始整体输入"与"拆解为多个可查询字段"双轨存储，**以原始输入为准**。
3. 提供可用的用户体系（账号、登录、操作留痕）；**权限体系暂不细分，登录后默认开放**。
4. **支持两种录入节奏**（见 §5.2"两种录入场景"）：
   - **现场分次增量填写**：一份表单在多个工序现场被逐步填写，每次保存只提交本次填写的内容；
   - **事后一次性完整录入**：表单收齐后次日由专人集中把整张表录入系统。
5. 同一表单号支持分次录入，系统保留**最新内容**，并保留每次保存的历史快照以备追溯。
6. 为后续的质量统计、良率趋势、不良分类分析留出数据基础。

### 1.3 非目标（本期不做）
- **不做审核/审批流程**：保存即录入生效（见 §5）。
- **不做精细的权限体系**：不区分角色与权限点，登录后默认开放全部功能（见 §3.1、§9 Q17）。
- **不做前端界面**：业务范围仅后端（见 §3.3）。
- 不做镜片检验设备 / AOI 的自动数据采集与对接。
- 不做 MES / ERP / 图纸系统的集成（预留接口位）。
- 不改变检验判定标准本身（系统只记录结果，不做缺陷自动判定）。
- 不做多工厂 / 多租户架构（预留 `org_id` 字段但本期单组织）。
- 不处理表格下方手写的率值行（如 `A：100%`）——**这是唯一与系统无关的手写内容**（见 §2.2 B-13）。
- 不解决"同一片镜片被计入多个不良类别"的重复计数问题（见 §9 Q5，登记为 `【待定】`）。

## 2. 名词与业务口径

### 2.1 表单标题
**镜片表面质量检验记录表**

### 2.2 业务口径（业务方口述确认）

| 编号 | 口径 | 状态 |
|---|---|---|
| B-1 | 「样品信息」在纸质表单上是一个独立项目，但其内容包含**多项信息**（见 §4.2 分层） | 【确认】 |
| B-2 | 纸质表单上「单位」与「表单号」之间那个没有栏目名的独立空格，实际是一个**独立项目：工序**，只是表单没有印制该栏名 | 【确认】 |
| B-3 | 该空格中的手写内容为 **「一次加硬」**（此前我方误读为"1R 加硬"） | 【确认】 |
| B-4 | 不良分类（点伤 / 划伤 / 脏污 / 加硬点 / 垃圾点）下的每一个子格（凹面 / 凸面 / 双面）填的是**该类不良的镜片数量**（不是比例、不是缺陷个数） | 【确认】 |
| B-5 | 本次任务范围：把这张手写表单做成线上系统 | 【确认】 |
| B-6 | 「样品信息」的内容**与部件号（图纸号）清单有关系，但不能确定生产部门就是照着该清单填写的**（存在沟通/习惯差异）。因此**一律以表单上的原始输入为准**，部件号清单仅作为结构化参考 | 【确认】 |
| B-7 | 「项目（M1 / M2）」等信息**必须纳入**系统的样品信息结构化录入 | 【确认】 |
| B-8 | 业务方**无法确认** `MONOC / BINOC / Rx` 等部件号附加成分的含义，也不掌握更多确切信息（唯一确切来源就是那张表单照片）。因此这部分**做到"有冗余字段更好、没有也能跑"即可**，不作为验收条件 | 【确认】 |
| B-9 | **同一份表单（同一表单号）会被分次录入**：真实流程是「一份空白表单 → 在各工序现场逐步填写 → 全部填完后收齐 → 次日由专人把完整的表录入系统」。系统将被用在哪个环节**尚未确定**，因此**必须同时支持分次增量填写与一次性完整录入**；同一表单号以**最新内容**为准 | 【确认】 |
| B-10 | **不需要审核流程**：用户保存即视为录入生效 | 【确认】 |
| B-11 | 表单上的既有栏目——**单位、送检人、送检时间、检验人、检验时间、操机员、交接员——都是系统必须纳入的字段**，不能省略 | 【确认】 |
| B-12 | 同一片镜片**可能同时被计入多个不良类别**，即各子项之和可能大于不良品数量 | 【确认】【待定】 |
| B-13 | **唯一可以无视的手写内容是表格下方的率值行**（如 `A：100%`）——它与本系统无关，不需要在系统中呈现 | 【确认】 |
| B-14 | 用户体系**暂不做严格的角色/权限划分**：生产部门会如何安排人员尚不明确，因此**登录后默认开放全部功能** | 【确认】 |
| B-15 | **交付范围仅后端**：业务方只负责后端部分，前端不需本期设计 | 【确认】 |

### 2.3 关键术语表

| 术语 | 含义 | 备注 |
|---|---|---|
| 工序 | 本记录对应的加工工序，如「一次加硬」 | 纸质表单未印栏名，线上系统必须补上 |
| 样品信息 | 部件/图号的原始书写形式，形如 `M2 S2 ND2 SMR` | 需双轨存储，见 §4.2 |
| 原始串（`sample_raw`） | 检验员在表单「样品信息」栏实际写下的整段内容 | **事实来源**，系统不得改写或"纠正" |
| 结构化字段 | 由原始串拆解出的可查询字段（项目/型号/规格/大小/左右 + 冗余） | 允许人工修正，修正不改写原始串 |
| 部件号（图纸号） | 参考清单中的规范编号，形如 `S1 - MD - R - VID2 - MONOC & BINOC`（序号 05~22） | **仅供参考**，不假定现场按此填写（B-6） |
| 表单（Form） | 一份纸质表单在系统中的主记录，以 `form_no` 标识 | 承载样品信息与表单级表头 |
| 表单记录（Record） | 表单下的一次工序填写记录，以 `sequence_no`（第几笔）标识 | 一份表单可有多笔，见 §5.2 |
| 分次录入（增量录入） | 在工序现场只填写并保存本次的内容，后续再补 | 支持按字段增量合并（B-9） |
| 一次性完整录入 | 表单收齐后，次日由专人一次性把整张表录入 | 与上者并存，同一接口支持（B-9） |
| 保存次数（`entry_seq`） | 同一条表单记录被保存的次数，从 1 开始 | 每次保存前留历史快照，见 §5 |
| 检验总数 | 本批次受检镜片片数 | |
| 合格品 | 检验合格的镜片片数 | |
| 不良品 | 检验判定为不良的镜片片数 | |
| 点伤 / 划伤 / 脏污 / 加硬点 / 垃圾点 | 五类表面不良 | 判定标准由业务方另行给出，见 §9 Q4 |
| 凹面 / 凸面 / 双面 | 每个不良类别下的三个计数维度 | 含义见 §9 Q5（`【待定】`） |

## 3. 用户与范围

### 3.1 用户体系（放开模式）

| 项 | 决定 |
|---|---|
| 定位 | 系统是"在线文档的增强版"，用户体系只用于**标识身份 + 留存操作痕迹**，不用于管控 |
| 角色 | **不设角色**（`【确认】` B-14）。登录后默认开放全部功能 |
| 权限 | **不做权限点校验**；保留一个"管理员"标记仅用于用户管理接口（见 §9 Q17） |
| 必须保留的能力 | 账号密码登录、修改密码、用户列表（姓名/工号/单位）、启用停用、**每条记录记录"谁在何时保存"** |
| 预留 | 代码结构上把"谁能做什么"抽成一层可替换的判定（当前恒为 true），便于生产部门明确安排后补上权限（见 §9 Q17） |

> 【确认】不设审核员、不设只读用户、不设审批动作（B-10、B-14）。
> 【待确认 Q17】是否需要区分一个**管理员**用于维护用户与字典？当前设计：保留 `is_admin` 布尔标记，仅保护"用户管理"接口，其余全部开放。

### 3.2 用户体系需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| U-1 | 账号 + 密码登录，密码以强哈希（Argon2id 或 bcrypt）存储，禁止明文/可逆加密 | P0 |
| U-2 | 用户具备唯一登录名、姓名、工号、所属单位/部门、状态（启用/停用）；**不再有角色字段** | P0 |
| U-3 | 首次登录强制修改初始密码；管理员可重置密码并强制再次修改 | P0 |
| U-4 | 登录失败次数限制与锁定（如 5 次失败锁定 10 分钟） | P1 |
| U-5 | 会话有效期 + 空闲超时；支持主动登出；移动端记住登录态 | P0 |
| U-6 | **不实现角色-权限模型**：登录后默认开放全部功能（B-14）。但代码需把"能否操作"抽成一层可替换判定，便于后续补权限 | P0 |
| U-7 | 停用用户立即失去登录能力，但其历史记录保留并可见其姓名 | P0 |
| U-8 | 操作日志：登录、登出、创建/保存/作废记录、用户与字典变更，含操作人、时间、IP、变更前后内容 | P0 |
| U-9 | 管理员可为用户重置密码、启用/停用（`is_admin` 标记，仅保护用户管理接口） | P0 |
| U-10 | 个人可修改自己的密码与显示名 | P1 |
| U-11 | **数据默认全部可见**（无行级权限过滤）；保留按单位/检验人的筛选能力即可 | P0 |
| U-12 | **保存留痕**：每次保存记录操作人、时间与旧内容快照，可追溯"谁在何时把什么改成了什么" | P0 |
| U-13 | 【待确认】是否对接企业微信 / 钉钉 / LDAP / AD 单点登录 | P2 |

### 3.3 交付范围（后端）

| 项 | 内容 |
|---|---|
| 本期交付 | **后端服务**：数据模型、业务逻辑（校验/保存/历史）、REST 接口、用户与登录、字典、统计与导出、审计 |

> 【确认】业务方只负责后端（B-15）。

## 4. 功能需求

### 4.1 记录填报（核心）

#### 4.1.1 表头字段

| 栏目（对应纸质表单） | 系统字段 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| 表单号 | `form_no` | 文本 | 是 | 如 `M-260908-01`。**表单主键**（一份表单一条主记录，其下可有多笔工序记录），支持自动生成与手工录入，见 §4.4、§5.2 |
| 样品信息（原始） | `sample_raw` | 文本 | 是 | 原始整体输入，逐字保留手写原貌；**事实来源**，系统不得改写（B-6） |
| 样品信息（拆解） | 见 §4.2 | 多字段 | 否 | 结构化轨；**项目（M1/M2）必须纳入**（B-7），其余尽量解析、可人工修正 |
| **工序**（纸质表单未印栏名） | `process` | 枚举 | 是 | 如「一次加硬」；**线上必须显式呈现为独立项目**（B-2、B-3） |
| 单位 | `unit_name` | 枚举/文本 | 是 | 表单既有栏目（B-11） |
| 送检人 | `submitted_by` | 文本/用户 | 是 | 表单既有栏目（B-11） |
| 送检时间 | `submitted_at` | 日期时间 | 是 | 表单既有栏目（B-11） |
| 检验人 | `inspected_by` | 文本/用户 | 是 | 表单既有栏目（B-11）；默认当前登录用户，可改 |
| 检验时间 | `inspected_at` | 日期时间 | 是 | 表单既有栏目（B-11）；默认当前时间，可改 |
| 操机员 | `machine_operator` | 文本/用户 | 是 | 表单既有栏目（B-11） |
| 交接员 | `handover_by` | 文本/用户 | 是 | 表单既有栏目（B-11） |
| 表格下方手写率值 | — | — | — | **不需要**（B-13）：如 `A：100%` 属表格下方手写内容，与系统无关，不建字段 |
| （系统维护字段） | `sequence_no` / `save_count` | 整数 | 系统 | 该表单下的第几笔记录 / 本条记录被保存的次数，见 §5.3 |
| （系统维护字段） | `recorded_by` / `recorded_at` | 用户/时间 | 系统 | 本条记录**由谁在何时录入系统**（区别于表单上的"检验人/送检人"，见 §9 Q18） |
| （系统维护字段） | `last_saved_by` / `last_saved_at` | 用户/时间 | 系统 | 本条记录最近一次由谁在何时保存 |

> 【确认】单位 / 送检人 / 送检时间 / 检验人 / 检验时间 / 操机员 / 交接员 **都是必须纳入的字段**（B-11），不再讨论"是否属于本期范围"。
> 【待确认 Q18】"次日由专人统一录入"意味着**表单上的检验人/送检人**与**实际录入系统的人**可能不是同一个。当前设计**拆成两组字段**：`inspected_by`/`submitted_by` 记录**表单上写的**（事实），`recorded_by` 记录**实际录入系统的人**（留痕）。请确认此理解。
> 【待确认】以上字段的"必填"强度：现场分次填写时可能一次填不全（见 §4.1.5 与 Q15）。当前设计：**允许暂缺，保存时给出缺失提示（V-10）**，不阻断。

#### 4.1.2 检验明细

一行 = 一个批次的计数录入（纸质表单一行）。字段与纸质表格列一一对应：

| 列 | 字段 | 类型 | 约束 |
|---|---|---|---|
| 检验总数 | `total_qty` | 整数 ≥ 0 | 必填 |
| 合格品 | `qualified_qty` | 整数 ≥ 0 | 必填 |
| 不良品 | `defect_qty` | 整数 ≥ 0 | 必填 |
| 点伤-凹面 | `spot_concave` | 整数 ≥ 0 | 可选（默认 0） |
| 点伤-凸面 | `spot_convex` | 整数 ≥ 0 | 可选（默认 0） |
| 点伤-双面 | `spot_both` | 整数 ≥ 0 | 可选（默认 0） |
| 划伤-凹面 | `scratch_concave` | 整数 ≥ 0 | 可选（默认 0） |
| 划伤-凸面 | `scratch_convex` | 整数 ≥ 0 | 可选（默认 0） |
| 划伤-双面 | `scratch_both` | 整数 ≥ 0 | 可选（默认 0） |
| 脏污-凹面 | `dirt_concave` | 整数 ≥ 0 | 可选（默认 0） |

#### 4.1.3 校验规则

> **总原则（在分次录入场景下尤其重要）**：**只有"数据自相矛盾"的错误才阻断保存；"还没填完"一律不阻断**，只记录缺失标记。
> 校验规则的"强/弱"由保存模式决定（见 §4.1.5）：**完整录入模式**下强校验生效；**增量录入模式**下 V-1/V-3/V-4 降级为警告。

| 编号 | 规则 | 级别 |
|---|---|---|
| V-1 | `qualified_qty + defect_qty = total_qty` | **完整录入模式**：错误（阻断）；**增量模式 / 计数未填时**：警告 |
| V-2 | `sum(五类不良的 15 个子项) = defect_qty` | **警告**（不阻断保存）。业务方已确认存在重复计数（B-12），本期仅提示"合计与不良品不一致"，留待 §9 Q5 解决 |
| V-3 | 各类别三子项之和 ≤ `defect_qty`；任一子项 ≤ `total_qty` | **完整模式**：错误；**增量模式**：警告 |
| V-4 | 所有计数为整数、非负；**完整模式**下要求 `total_qty > 0` | 完整模式：错误；增量模式：警告（仅校验非负整数） |
| V-5 | 良率 = `qualified_qty / total_qty × 100%`，保留 1~2 位小数；跨行/整单良率 = `Σ合格品 / Σ检验总数` | 计算 |
| V-6 | 送检时间不得晚于检验时间；检验时间不得晚于当前时间 | **警告**（纸质表单上这两个时间常为人工补记，硬性阻断不合理）。`【假设】` |
| V-7 | `form_no` 作为**表单**唯一；同一表单下 `(form_no, sequence_no)` 唯一 | 错误（唯一索引兜底） |
| V-8 | 样品信息拆解字段与参考部件号清单不匹配 | 警告（允许保存，仅标记"待核对"，见 §4.2.4）。**不得因不匹配而阻断录入**（B-6、B-8） |
| V-9 | 结构化必填项（**项目 M1/M2**）为空 | 警告（可保存为"待补全"）。`【假设】` 保持警告，避免现场被迫中断录入 |
| V-10 | **表单既有栏目缺失**（单位/送检人/送检时间/检验人/检验时间/操机员/交接员 任一为空） | 警告 + 返回缺失字段清单（B-11 要求这些字段**必须存在**，但不因"暂未填"而阻断分次录入） |

| 编号 | 需求 | 优先级 |

#### 4.1.5 两种录入场景（关键需求）

> **背景（业务方原话概括）**：一份空白表单从每个工序开始逐步填写，全部填完后收集到一起，**等第二天由专门的人员把完整的表写进系统（现状用 Excel）**。但系统最终会被用在**工序现场填写**还是**最终集中录入**，业务方目前也不知道。

因此系统**必须同时支持两种模式**，且同一份表单的数据在两种模式下产生的结果应当一致：

| 模式 | 典型场景 | 后端行为 |
|---|---|---|
| **A. 增量录入（按笔/按工序）** | 工序现场用手机逐步填；或录入员分几次补录 | 每次保存只更新**本次提交的字段**（`PATCH` 语义，字段级合并），未提交的字段保持原值；校验降级为警告；`entry_seq` 自增并留快照 |
| **B. 一次性完整录入** | 次日由专人把整张表一次录入 | 一次提交完整表单；执行强校验；形成 1 笔（或 N 笔按工序）完整记录 |

**两种模式的统一方式（避免两套模型）**：

| 设计点 | 做法 |
|---|---|
| 同一份表单一笔记录的多次保存 | **字段级合并更新**（未提交字段不变），而非整体替换 —— 这是为了兼容"不同工序由不同人填不同字段" |
| 多工序如何落库 | 用 `sequence_no` 区分"第几笔"，每笔带自己的 `process`（工序）与人员/时间字段。**现场分次填时**：每个工序保存为独立一笔；**集中录入时**：一次提交可包含多笔（数组） |
| 条件 | 说明 |
|---|---|
| 校验强度 | 由请求参数 `mode: incremental \| full` 决定（§4.1.3） |
| 完成度 | 每笔记录有 `is_complete` 标记（由 V-10 缺失项计算），并提供"某表单下所有笔是否都已完整"的汇总 |
| 历史 | 每次保存（无论哪种模式）都把**保存前的内容**写入历史快照 |

> 【待确认 Q19】**多工序是"一份表单一行/一笔"还是"每道工序各一笔"**？这直接决定 `sequence_no` 的语义：
> - (a) 纸质表单上每个工序现场各填写**一行**（同一张表上，不同行 = 不同工序）→ 那么"一份表"= 一份表单 + 多行，行内需带工序；
> - (b) 每个工序现场填写的是**同一张表单的同一组栏目**，只是分次补齐（最终仍是一行）→ 那么"一笔"就足够，多次保存只是字段合并。
> 当前设计**兼容两者**：`sequence_no`（笔）+ 笔内 `lines`（行），工序既可落在笔上也可落在行上。**请业务方确认哪种符合现实**，以便收敛字段归属。


### 4.2 样品信息（重点需求）

#### 4.2.1 双轨存储

业务方明确要求样品信息**两类存储并存**：

- **原始轨 `sample_raw`**：整段原始输入，形如 `M2 S2 ND2 SMR`（示例按表单照片），逐字保留，永不改写。作为事实来源（source of truth）。
- **结构化轨**：系统录入时将原始串拆解为多个独立字段，用于查询、筛选、统计、分组。

原始轨不做任何规范化或纠正；结构化轨允许人工修正，且两者不一致时以原始轨为准，并记录差异标记。

#### 4.2.2 拆解字段与层级

业务方给出的层级（示例导向）：

```
项目        （M1 / M2）
 └ 型号     （VID1 RX / VID2）
    └ 规格  （S1 / S2）
       └ 大小（MD / SM）
          └ 左右（L / R）
```

同时，由业务方给出的部件号列表（§4.2.3）可看出还存在**两个附加成分**：

| 附加成分 | 取值 | 我方理解 | 状态 |
|---|---|---|---|
| 结构类别 | `MONOC` / `BINOC` / `MONOC & BINOC` | Monocular / Binocular（单目 / 双目），表示该部件适用的产品构型 | 【假设】【确认无法确认】 |
| 处方属性 | `Rx`（或写作 `RX`） | 处方镜（prescription），出现在 `VID1 Rx` 型号中 | 【假设】【确认无法确认】 |

> **重要（业务方第二轮确认，B-6 / B-8）**：业务方**只能确认"样品信息项的内容与部件号清单有关系"，但无法确认生产部门实际就是照该清单填写的**（存在部门间沟通/习惯差异），并且**无法确认** `MONOC / BINOC / Rx` 等附加成分的准确含义——业务方唯一确切的信息来源就是那张表单照片。
>
> 由此产生一条贯穿全局的设计原则：
> **① 以表单上的原始输入为准（`sample_raw` 为事实来源）；② 部件号清单与附加成分只作为"尽力而为"的冗余参考，解析不到、对不上都不得阻断录入、不得作为验收条件。**
>
> （原业务方表述："把已有信息做好即可……有冗余更好，但没有也能跑。"）

因此设计为：
- **五个核心拆解字段**：**项目（M1/M2）必须纳入表单并作为结构化录入项**（B-7）；型号 / 规格 / 大小 / 左右尽量解析并允许人工修正。
- **冗余（扩展）字段** `MONOC/BINOC` 与 `Rx`：尽力解析填充，解析不到留空，**不参与任何校验，不作为验收条件**（B-8）。

核心五字段（结构化轨）：

| 层级 | 字段 | 示例值 | 字典/取值 | 要求 |
|---|---|---|---|---|
| 1 项目 | `sample_project` | `M2` | M1 / M2 | **必须纳入**（B-7） |
| 2 型号 | `sample_model` | `VID2` | VID1 Rx / VID2 | 尽量解析，可人工修正 |
| 3 规格 | `sample_spec` | `S2` | S1 / S2 | 尽量解析，可人工修正 |
| 4 大小 | `sample_size` | `SM` | MD / SM / LG | 尽量解析，可人工修正 |
| 5 左右 | `sample_side` | `R` | L / R | 尽量解析，可人工修正 |

冗余（扩展）字段（**均可空、不校验、不作为验收条件**）：

| 字段 | 示例值 | 说明 |
|---|---|---|
| `sample_class`（结构类别） | `MONOC` / `BINOC` / `MONOC_AND_BINOC` | 可多选（一个部件可能同时适用单目与双目）；**含义未确认** |
| `sample_is_rx`（处方镜） | `true` / `false` | 型号含 `Rx` / `RX` 时为 true；**含义未确认** |
| `sample_drawing_no`（匹配到的参考部件号） | `S2 - SM - R - VID2 - MONOC` | 来自 §4.2.3 参考清单，**仅供参考** |

| `sample_unmatched_reason` | `raw_only` / `no_drawing` / `partial` | 未匹配原因，驱动"待核对"清单 |

> 【保留的设计提醒】层级顺序与字符串书写顺序不一致：业务方描述的层级是 项目 → 型号 → 规格 → 大小 → 左右，而参考清单中部件号的**书写顺序**是 `规格 - 大小 - 左右 - 型号 - 结构类别`（如 `S1 - MD - R - VID2 - MONOC & BINOC`）。系统以**字段**为准，**解析器按 token 集合识别而非按位置解析**。

## 5. 记录生命周期与分次录入

> **本节依据业务方第二、三轮确认**：无审核流程（B-10）；一份表单在多个工序现场逐步填写，全部填完后次日由专人统一录入（B-9）；保存即生效。

### 5.1 数据组织原则："一份表单 + 多笔工序记录 + 追加式历史"

**不设计 DRAFT / SUBMITTED / APPROVED / REJECTED 审批状态机。** 保存即录入生效。

```
┌─────────────────────────────────────────────────────────────────────┐
│  表单 Form（form_no = M-260908-01）                                  │
│  ├─ 样品信息（sample_raw + 结构化字段）      ← 表单级，填一次即固定    │
│  ├─ 单位 / 表单创建者 / 创建时间                                     │
│  │                                                                  │
│  ├─ 第1笔 Record（sequence_no = 1）  process = 一次加硬               │
│  │    ├─ 送检人/送检时间/检验人/检验时间/操机员/交接员                 │
│  │    ├─ 计数明细 lines[]（检验总数、合格品、不良品、15 个不良子项）   │
│  │    └─ 保存历史 history[]（每次保存前的快照）                       │
│  │                                                                  │
│  ├─ 第2笔 Record（sequence_no = 2）  process = 二次加硬               │
│  │    └─ …（同上结构，可由另一位检验员在不同时间填写）                 │
│  └─ …                                                              │
└─────────────────────────────────────────────────────────────────────┘
```

**为什么是"表单 + 多笔"而不是"一表单号一条记录"**：纸质表单要在多个工序中使用，各工序的检验发生在不同时间、可能由不同人填写。若只有一条记录，每次保存就得整体替换，历史信息（谁在哪个工序填了什么）会被覆盖掉。拆成"笔"后：

- 每笔**只被本次填写的内容更新**（字段级合并），互不干扰；
- 每笔有独立的工序、人员、时间；
- 每笔有自己的历史快照，追溯粒度贴合实际。

> 【待确认 Q19】若现实中每个工序是**在同一张表上各填一行**（而不是各写一组表头栏目），则"行"应携带工序，模型需把 `process` 下移到 `line`。【设计决定】当前**笔与行都保留工序字段**，两种现实都能表达，待确认后收敛。

### 5.2 两种录入场景（必须同时支持）

| 模式 | 场景 | 请求语义 | 校验强度 |
|---|---|---|---|
| **A. 增量录入** | 工序现场分次填；或录入员分次补录 | `PATCH` 语义：**只更新本次提交的字段**，未提交字段保持原值；明细若提交则替换该笔明细 | 弱（V-1/V-3/V-4 降级为警告，V-10 提示缺失） |
| **B. 一次性完整录入** | 次日由专人把整张表一次录入 | 一次性提交完整内容：可同时提交**表单信息 + 多笔记录 + 每笔明细** | 强（V-1/V-3/V-4 生效） |

**统一性要求**：两种模式产生的**数据结构与最终内容必须一致**，不得因录入方式不同而产生不同形态的数据。因此：

- 保存走同一套接口，通过 `mode` 参数区分校验强度；
- 无论哪种模式，每次保存都写历史快照；
- 无论哪种模式，服务端都重算汇总与良率；
- 完整性由 `is_complete`（依据缺失项计算）表达，而不是靠"必须一次填完"来保证。

### 5.3 保存规则

| 编号 | 规则 |
|---|---|
| L-1 | `form_no` 标识**表单**；`(form_no, sequence_no)` 标识**一笔工序记录** |
| L-2 | 保存时若 `(form_no, sequence_no)` 已存在 → **更新该笔**（字段级合并；明细提交则替换），该笔 `save_count` 自增；不存在 → 新建该笔 |
| L-3 | 每次保存前，把**该笔保存前的完整内容**（含明细、结构化字段、原始串、人员时间字段）写入历史表，并记录操作人、时间、IP。历史**不可修改、不可删除** |
| L-4 | **字段级合并**是默认语义（为兼容"不同工序/不同人只填自己那部分"）。如需强制整体替换，请求显式传 `mode: full` 或 `overwrite: true` |
| L-5 | 并发：以该笔的 `save_count` / `updated_at` 作乐观锁；不一致时返回 `409` + 差异，由调用方决定是否重试 |
| L-6 | 记录**不做物理删除**；如需废弃用"作废（VOID）"标记并记录原因，作废记录默认不出现在统计中 |
| L-7 | 允许保存**不完整**内容（如只填了工序与样品信息、计数还没填）：此时 `is_complete = false` 并返回缺失字段清单 |
| L-8 | 表单级与笔级字段都可更新；表单级字段（样品信息、单位）更新同样留快照 |
| L-9 | **无权限门槛**：任何已登录用户都可保存/更新任意表单与笔（B-14），但**必须留痕** |
| L-10 | 汇总（`total_qty` / `qualified_qty` / `defect_qty` / 良率）由服务端按笔重算落库，供查询与统计直接使用 |

### 5.4 字段更新语义速查

| 内容 | 更新方式 | 说明 |
|---|---|---|
| `sample_raw`、结构化字段（表单级） | 字段级合并 | 传了才改；历史快照保留旧值（原始串可能被重新书写） |
| `process`、单位、人员、时间（笔级） | 字段级合并 | 不同工序/不同人各自填写 |
| 计数明细行（lines） | 提交则**整笔替换**（不做行级合并） | 避免"半行数据"歧义；行级粒度不值得做合并 |
| `created_by` / `created_at` | 不更新 | 表单创建者与时间永不改变 |
| `recorded_by` / `recorded_at` | 首次保存时写入 | 表示"谁把它录进系统"（区别于表单上的检验人） |
| `last_saved_by` / `last_saved_at` | 每次保存更新 | 最近一次保存的人与时间 |
| `save_count` | 递增 | 该笔被保存的次数 |
| `is_complete` / `missing_fields` | 每次保存重算 | 依据 V-10 等缺失项 |
| 历史与操作日志 | 只增 | 不可修改、不可删除 |

### 5.5 状态取值（极简）

| 状态 | 说明 |
|---|---|
| `ACTIVE` | 已录入生效（默认，唯一正常状态） |
| `VOID` | 已作废（逻辑标记 + 原因；保留全部数据与历史） |

### 5.6 完成度（多工序汇总）

| 需求 | 说明 |
|---|---|
| 单笔完成度 | `is_complete` + `missing_fields[]`（V-10 缺失项） |
| 表单完成度 | 表单下所有笔是否都 `is_complete`；提供"未完成表单清单"查询，便于跟进次日集中录入的进度 |
| 备注 | `【待确认】` 是否需要"应经过哪些工序"的清单（工序完整性校验）——目前不知道一份表单要走哪些工序，暂不做 |

## 8. 验收标准（初稿，后端视角）

1. **场景 A（现场分次增量填写）**：同一份表单分 3 次（不同工序、不同人）保存，每次只提交本次字段；最终记录能正确合并出完整内容，且每次保存的历史快照与字段级差异都可查询。
2. **场景 B（次日一次性完整录入）**：一次请求提交整张表（含全部既有栏目与计数明细），强校验生效，结果与场景 A 的最终内容等价。
3. 表单既有栏目**全部存在**：单位 / 送检人 / 送检时间 / 检验人 / 检验时间 / 操机员 / 交接员 均可写入与读出（B-11）；缺失时返回缺失清单（V-10）。
4. 样品信息支持原始串录入 + 自动拆解为 5 个核心字段（含**项目 M1/M2**）与冗余字段，且可人工修正；**修正与解析均不改写原始串**。
5. 按 `sample_size = SM`、`process = 一次加硬`、日期区间等条件可正确检索到记录（验证索引有效）。
6. 校验行为正确：完整模式下 V-1 阻断；增量模式下 V-1 仅警告；V-2 恒为警告；良率计算与手工核算一致。
7. 用户体系可完成：创建用户 → 首次登录改密 → 停用后无法登录；**除用户管理外不因缺少权限而被拒绝**（B-14）。
8. 每次保存均可追溯（含操作人、时间、前后内容），且"表单上的检验人"与"实际录入人"两个信息都能读出。
9. 表单号并发生成 100 次无重号；同一表单下 `(form_no, sequence_no)` 唯一。
10. 导出的 Excel/CSV 与查询结果一致。

| **Q20** | 系统最终用在**哪个环节**（工序现场 / 最终集中录入 / 两者都用）？ | **待确认**（业务方当前不知道） | 当前设计按"两者都用"实现，因此**不能用任何环节的假设去简化校验强度** |
