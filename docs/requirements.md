> **v0.4 主要变更**（依据业务方第四轮确认）
> 1. **"最大灵活性"上升为第一设计原则**（见 §1.4）：生产部门流程繁杂且无法详细确认，因此**系统不做任何流程约束**——不强制字段、不强制顺序、不强制完整、不强制工序集合。
> 2. **多工序落库形态（原 Q19）明确为"不确认"** → 工序字段在"笔"与"行"上**都保留**，两种现实都能表达，不收敛。
> 3. **人 vs 系统用户的区分（原 Q18）**：表单上的人员（送检人/检验人/操机员/交接员）按**纸面文字**记录；同时用**系统用户**记录"谁创建/谁最后更新/谁做的本次修改"，用于追溯，**不绑定真实人员身份**。
> 4. **用户体系**保留最基本的 **管理员 / 普通用户** 两级区分（原 Q17 确认）。
> 5. **新增需求：汇总统计**（按样品信息的各子项聚合），本期**纳入需求但不实现**，待框架搭好后做（见 §4.7）。
> 6. **明确控制复杂度**：本系统是"在线文档的升级版"，**不做过度设计**（见 §1.4）。

> **v0.5 主要变更**（依据业务方第五轮说明与表单列清单截图）
> 1. **场景澄清**：**每道工序都要填一份表单，只是各工序所填内容不同**；系统的一个"表单提交"就是**一次工序填写**。原来假设的"一张表单 + 多笔工序记录"**作废**。
> 2. **表单列目录落地**：顶层栏目 5 个（检验工序/检验总数/合格品/不合格品/合格率）+ **不良缺陷明细 35 列**，每列含 **凹面/凸面/双面** 三个计数 → **105 个子列**（见 §5.2）。
> 3. **列清单单一来源**：集中在后端字段目录里，接口下发给前端；`form_lines` 的列也由该目录生成，新增列只改目录 + 一次迁移。
> 4. **工序上移到提交**（`operation_code`，表单第一列），并成为检索与统计的主维度；**未登记的工序同样合法**（按通用模板处理，开放全部列）。
> 5. **字段级合并明确三态**：键不存在=不改 / `null`=清空 / 有值=写入；缺陷格子同样支持 `null` 清零；未知字段报 400 并提示合法列。
> 6. **表头与明细的优先级**：补丁里显式给出的表头栏目优先，否则按明细行重算。
> 7. §5 整节重写；新增 §5.2 列目录、§5.6 幂等；统计口径改为按表单提交。

> **标注约定**：`【确认】` = 业务方已明确说明；`【待确认】` = 尚未确认的假设；`【假设】` = 我方为保证可设计性先行的默认决定；`【待定】` = 业务方已知问题并明确**延后处理**；`【暂缓】` = 已确认需要，但**本期不实现**。
>
> **字段命名约定**：需求文档使用 `snake_case`（`sample_raw`、`sequence_no`），设计文档 §4 的 Go/DB 结构使用同名 `snake_case` 列 + `CamelCase` 结构体字段。**同一字段，只有书写风格差异**。

## 1. 背景与目标

### 1.1 背景
镜片（含 KF / EVT 相关产品部件）在加硬等工序后需要进行表面质量检验，目前使用纸质表单《镜片表面质量检验记录表》逐批手写记录，存在以下问题：

- 纸质记录难以查询、统计与追溯（按批次、部件号、检验人、日期检索几乎不可行）。
- 手写内容不规范（如"一次加硬"被写在没有栏目名的空格里），无法结构化汇总。
- 不良分类（点伤 / 划伤 / 脏污 / 加硬点 / 垃圾点 × 凹面 / 凸面 / 双面）数据无法沉淀为质量分析依据。

### 1.2 目标
将纸质表单线上化，形成**可录入、可校验、可检索、可统计、可追溯**的检验记录系统。产品定位是**"在线文档的增强版"**——把手工填表变成线上录入，而不是引入审批与流程管控的业务系统：

1. 线上填报表单，**字段与纸质表单一一对应，不遗漏任何一个既有栏目**，不改变现场检验人员的判定口径。
2. 样品信息支持"原始整体输入"与"拆解为多个可查询字段"双轨存储，**以原始输入为准**。
3. 提供可用的用户体系（账号、登录、操作留痕）；**权限体系暂不细分，登录后默认开放**。
4. **支持两种录入节奏**（见 §5.2"两种录入场景"）：
   - **现场分次增量填写**：一份表单在多个工序现场被逐步填写，每次保存只提交本次填写的内容；
   - **事后一次性完整录入**：表单收齐后次日由专人集中把整张表录入系统。
5. 同一表单号支持分次录入，系统保留**最新内容**，并保留每次保存的历史快照以备追溯。
6. 为后续的质量统计、良率趋势、不良分类分析留出数据基础。

### 1.4 第一设计原则：最大灵活性（【确认】）

业务方原话要点：**生产部门的流程比较繁杂，无法详细确认，因此一律以最大灵活性要求出发进行设计**；本系统只是"在线文档的升级版"，**无需设计得太复杂**。

由此得出**硬性设计约束**（后续所有设计不得违反）：

| 编号 | 约束 | 含义 |
|---|---|---|
| F-1 | **不强制任何字段**（`form_no` 之外） | 除表单号外，任何字段都允许为空保存 |
| F-2 | **不强制任何顺序** | 可以先填计数后填样品信息；可以先建笔后补表单信息 |
| F-3 | **不强制完整性** | 允许保存"填了一半"的内容，只提示不阻断 |
| F-4 | **不约束工序集合** | 不知道也不校验"一份表单应经过哪些工序"，工序可自由新增 |
| F-5 | **不假设使用环节** | 工序现场分次填、次日集中录入、混合使用都必须能跑（不因任一假设收紧校验） |
| F-6 | **不收敛未知语义** | 无法确认的信息（部件号附加成分、多工序形态）用"两者都保留 + 可空"处理，不做唯一化 |
| F-7 | **默认只警告不阻断** | 校验默认全部为**警告**；只有调用方显式要求 `enforce=strict` 时才返回阻断错误 |
| F-8 | **可扩展优先于精确** | 字典驱动（工序/单位/样品段/部件号/不良列），新增取值不需要改代码或发版 |

> **推论**：系统在数据层面几乎不"拒绝"输入。数据质量靠**提示**（缺失项、可疑项）与**追溯**（历史快照）保障，而不是靠拒绝。

### 1.5 非目标（本期不做）

- **不做审核/审批流程**：保存即录入生效（见 §5）。
- **不做精细的权限体系**：只保留"管理员 / 普通用户"两级（见 §3.1）。
- **不做前端界面**：业务范围仅后端（见 §3.3）。
- **汇总统计本期不实现**：需求已确认（§4.7），待工程骨架搭好后实施（`【暂缓】`）。
- 不做镜片检验设备 / AOI 的自动数据采集与对接。
- 不做 MES / ERP / 图纸系统的集成（预留接口位）。
- 不改变检验判定标准本身（系统只记录结果，不做缺陷自动判定）。
- 不做多工厂 / 多租户架构。
- 不处理表格下方手写的率值行（如 `A：100%`）——**这是唯一与系统无关的手写内容**（见 §2.2 B-13）。
- 不解决"同一片镜片被计入多个不良类别"的重复计数问题（见 §9 Q5，登记为 `【待定】`）。

## 2. 名词与业务口径

### 2.1 表单标题
**镜片表面质量检验记录表**

### 2.2 业务口径（业务方口述确认）

| 编号 | 口径 | 状态 |
|---|---|---|
| B-1 | 「样品信息」在纸质表单上是一个独立项目，但其内容包含**多项信息**（见 §4.2 分层） | 【确认】 |
| B-2 | 纸质表单上「单位」与「表单号」之间那个没有栏目名的独立空格，实际是一个**独立项目：工序**，只是表单没有印制该栏名 | 【确认】 |
| B-3 | 该空格中的手写内容为 **「一次加硬」**（此前我方误读为"1R 加硬"） | 【确认】 |
| B-4 | 不良分类（点伤 / 划伤 / 脏污 / 加硬点 / 垃圾点）下的每一个子格（凹面 / 凸面 / 双面）填的是**该类不良的镜片数量**（不是比例、不是缺陷个数） | 【确认】 |
| B-5 | 本次任务范围：把这张手写表单做成线上系统 | 【确认】 |
| B-6 | 「样品信息」的内容**与部件号（图纸号）清单有关系，但不能确定生产部门就是照着该清单填写的**（存在沟通/习惯差异）。因此**一律以表单上的原始输入为准**，部件号清单仅作为结构化参考 | 【确认】 |
| B-7 | 「项目（M1 / M2）」等信息**必须纳入**系统的样品信息结构化录入 | 【确认】 |
| B-8 | 业务方**无法确认** `MONOC / BINOC / Rx` 等部件号附加成分的含义，也不掌握更多确切信息（唯一确切来源就是那张表单照片）。因此这部分**做到"有冗余字段更好、没有也能跑"即可**，不作为验收条件 | 【确认】 |
| B-9 | **同一份表单（同一表单号）会被分次录入**：真实流程是「一份空白表单 → 在各工序现场逐步填写 → 全部填完后收齐 → 次日由专人把完整的表录入系统」。系统将被用在哪个环节**尚未确定**，因此**必须同时支持分次增量填写与一次性完整录入**；同一表单号以**最新内容**为准 | 【确认】 |
| B-10 | **不需要审核流程**：用户保存即视为录入生效 | 【确认】 |
| B-11 | 表单上的既有栏目——**单位、送检人、送检时间、检验人、检验时间、操机员、交接员——都是系统必须纳入的字段**，不能省略 | 【确认】 |
| B-12 | 同一片镜片**可能同时被计入多个缺陷类别**，即各子项之和可能大于不合格品数量 | 【确认】【待定】 |
| B-13 | **唯一可以无视的手写内容是表格下方的率值行**（如 `A：100%`）——它与本系统无关，不需要在系统中呈现 | 【确认】 |
| B-14 | 用户体系暂不做严格划分，但**保留"管理员 / 普通用户"这一最基本区分**，登录后普通用户默认开放全部业务功能 | 【确认】 |
| B-15 | **交付范围仅后端**：业务方只负责后端部分，前端不需本期设计 | 【确认】 |
| B-16 | **最大灵活性优先**：生产部门流程繁杂且无法确认，系统**不做流程约束**（不强制字段、顺序、完整性、工序集合），详见 §1.4 的 F-1~F-8 | 【确认】 |
| B-17 | 表单上的人员（送检人/检验人/操机员/交接员）按**纸面上的文字**记录；同时用**系统用户**记录"谁创建、谁最后更新、谁做了本次修改"，**仅用于追溯，不绑定真实人员身份** | 【确认】 |
| B-18 | 需要**按样品信息各子项做汇总**的功能；本期**先纳入需求、暂不实现** | 【确认】【暂缓】 |
| B-19 | 本系统只是"在线文档的升级版"，**不要设计得太复杂**（复杂度控制是明确要求） | 【确认】 |

### 2.3 关键术语表

| 术语 | 含义 | 备注 |
|---|---|---|
| 工序 | 本记录对应的加工工序，如「一次加硬」 | 纸质表单未印栏名，线上系统必须补上 |
| 样品信息 | 部件/图号的原始书写形式，形如 `M2 S2 ND2 SMR` | 需双轨存储，见 §4.2 |
| 原始串（`sample_raw`） | 检验员在表单「样品信息」栏实际写下的整段内容 | **事实来源**，系统不得改写或"纠正" |
| 结构化字段 | 由原始串拆解出的可查询字段（项目/型号/规格/大小/左右 + 冗余） | 允许人工修正，修正不改写原始串 |
| 部件号（图纸号） | 参考清单中的规范编号，形如 `S1 - MD - R - VID2 - MONOC & BINOC`（序号 05~22） | **仅供参考**，不假定现场按此填写（B-6） |
| 表单（Form） | 一份纸质表单在系统中的主记录，以 `form_no` 标识 | 承载样品信息与表单级表头 |
| 表单提交（Submission） | **一次工序填写 = 某工序填的那张表单**，以 `form_no` 标识 | 见 §5.1 |
| 分次录入（增量录入） | 在工序现场只填写并保存本次的内容，后续再补 | 支持按字段增量合并（B-9） |
| 一次性完整录入 | 表单收齐后，次日由专人一次性把整张表录入 | 与上者并存，同一接口支持（B-9） |
| 保存次数（`entry_seq`） | 同一条表单记录被保存的次数，从 1 开始 | 每次保存前留历史快照，见 §5 |
| 检验总数 | 本批次受检镜片片数 | |
| 合格品 | 检验合格的镜片片数 | |
| 不合格品 | 检验判定为不合格的镜片片数 | 表单第 4 列 |
| 点伤 / 划伤 / 脏污 / 加硬点 / 垃圾点 | 五类表面不良 | 判定标准由业务方另行给出，见 §9 Q4 |
| 凹面 / 凸面 / 双面 | 每个不良类别下的三个计数维度 | 含义见 §9 Q5（`【待定】`） |

## 3. 用户与范围

### 3.1 用户体系（两级：管理员 / 普通用户）

| 项 | 决定 |
|---|---|
| 定位 | 系统是"在线文档的升级版"，用户体系只用于**标识身份 + 留存操作痕迹**，不用于管控业务 |
| 级别 | **只有两级**（`【确认】` B-14）：`admin`（管理员）与 `user`（普通用户）。不设角色、不设权限点 |
| 差异 | **普通用户**：可读写全部业务数据（表单、笔、明细、字典、统计、导出、历史）。**管理员**：额外可管理用户（创建/启停/重置密码/设管理员） |
| 必须保留 | 账号密码登录、修改密码、用户列表（姓名/工号/单位）、启用停用、**每条记录记录"谁创建 / 谁最后更新 / 谁做的本次修改"**（B-17） |
| 人员字段 | 表单上的送检人/检验人/操机员/交接员是**纸面文字**，与系统用户无关，不做账号绑定（B-17） |
| 预留 | 把"谁能做什么"抽成一层可替换判定（当前仅两级），将来若需细分，不改业务代码 |

> 【确认】不设审核员、不设只读用户、不设审批动作（B-10、B-14）。管理员标记**不可自助修改**。

### 3.2 用户体系需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| U-1 | 账号 + 密码登录，密码以强哈希（Argon2id 或 bcrypt）存储，禁止明文/可逆加密 | P0 |
| U-2 | 用户具备唯一登录名、姓名、工号、所属单位/部门、级别（`admin`/`user`）、状态（启用/停用） | P0 |
| U-3 | 首次登录建议修改初始密码；管理员可重置密码 | P0 |
| U-4 | 登录失败次数限制与锁定（如 5 次失败锁定 10 分钟） | P1 |
| U-5 | 会话有效期 + 空闲超时；支持主动登出 | P0 |
| U-6 | **只有两级判定**：`admin` 才能调用用户管理接口；其余业务接口对任何已登录用户开放（B-14） | P0 |
| U-7 | 停用用户立即失去登录能力，但其历史记录保留并可见其姓名 | P0 |
| U-8 | 操作日志：登录、登出、创建/保存/作废记录、用户与字典变更，含操作人、时间、IP、变更前后内容 | P0 |
| U-9 | 管理员可为用户重置密码、启用/停用、设置/取消管理员 | P0 |
| U-10 | 个人可修改自己的密码与显示名 | P1 |
| U-11 | **数据默认全部可见**（无行级权限过滤）；保留按单位/检验人的筛选能力即可 | P0 |
| U-12 | **保存留痕**：每次保存记录"系统用户 + 时间 + 保存前内容快照"，可追溯"哪个账号在何时把什么改成了什么"（B-17） | P0 |
| U-13 | 【待确认】是否对接企业微信 / 钉钉 / LDAP / AD 单点登录 | P2 |

### 3.3 交付范围（后端）

| 项 | 内容 |
|---|---|
| 本期交付 | **后端服务**：数据模型、业务逻辑（校验/保存/历史）、REST 接口、用户与登录、字典、统计与导出、审计 |
| 本期不交付 | 前端界面。文档中出现的"页面/路由"仅作为**接口使用场景说明**，不是开发任务 |
| 前端契约 | 后端需提供稳定的接口契约（§6）与共享校验规则说明（可导出 OpenAPI），以便他人对接 |

## 4. 功能需求

### 4.1 记录填报（核心）

#### 4.1.1 表头栏目（5 个）

#### 4.1.3 校验规则

> **总原则（F-3、F-7）**：**默认只警告，不阻断。** 由请求参数 `enforce` 控制：
> `warn`（默认）任何内容都能保存；`strict` 时下表标 ⛔ 的规则升级为阻断（422）。
> 唯一的硬性阻断与内容无关：**登录态**、**`form_no` 与 `(form_id, seq)` 唯一性**。

| 编号 | 规则 | 默认（`warn`） | `strict` 时 |
|---|---|---|---|
| V-1 | 合格品 + 不合格品 = 检验总数（三者全为 0 时不提示） | 警告 | ⛔ 阻断 |
| V-2 | 缺陷子项合计 = 不合格品 | **恒为警告**（已确认会重复计数 B-12，登记 `【待定】`） | 警告 |
| V-3 | 某缺陷列三表面合计 ≤ 不合格品；单个子列 ≤ 检验总数 | 警告 | ⛔ 阻断 |
| V-4 | 所有计数为非负整数 | 警告 | ⛔ 阻断 |
| V-5 | 合格率 = 合格品 / 检验总数 | 计算 | 计算 |
| V-6 | 提交时间不得晚于当前时间 | 警告 | 警告（纸面时间常为补记） |
| V-7 | `form_no` 唯一；`(form_id, seq)` 唯一 | ⛔ 阻断（409） | ⛔ 阻断 |
| V-8 | 样品信息与参考部件号清单不匹配 | 警告（+ 待核对标记） | 警告（**不得阻断**，B-6/B-8） |
| V-9 | 样品结构化项（项目 M1/M2）缺失 | 警告 | 警告 |
| V-10 | 表单栏目缺失（检验工序 / 单位 / 样品原始串 / 明细） | 警告 + `missing_fields` | 警告 |
| V-11 | 未知字段名 | ⛔ 阻断（400，提示合法列清单） | ⛔ 阻断 |

**设计要点**：V-2/V-5/V-6/V-8/V-9/V-10 **在任何模式下都不阻断**——它们描述"业务上还不确定"或"还没填完"。

### 4.2 样品信息（重点需求）

#### 4.2.1 双轨存储

业务方明确要求样品信息**两类存储并存**：

- **原始轨 `sample_raw`**：整段原始输入，形如 `M2 S2 ND2 SMR`（示例按表单照片），逐字保留，永不改写。作为事实来源（source of truth）。
- **结构化轨**：系统录入时将原始串拆解为多个独立字段，用于查询、筛选、统计、分组。

原始轨不做任何规范化或纠正；结构化轨允许人工修正，且两者不一致时以原始轨为准，并记录差异标记。

#### 4.2.2 拆解字段与层级

业务方给出的层级（示例导向）：

```
项目        （M1 / M2）
 └ 型号     （VID1 RX / VID2）
    └ 规格  （S1 / S2）
       └ 大小（MD / SM）
          └ 左右（L / R）
```

同时，由业务方给出的部件号列表（§4.2.3）可看出还存在**两个附加成分**：

| 附加成分 | 取值 | 我方理解 | 状态 |
|---|---|---|---|
| 结构类别 | `MONOC` / `BINOC` / `MONOC & BINOC` | Monocular / Binocular（单目 / 双目），表示该部件适用的产品构型 | 【假设】【确认无法确认】 |
| 处方属性 | `Rx`（或写作 `RX`） | 处方镜（prescription），出现在 `VID1 Rx` 型号中 | 【假设】【确认无法确认】 |

> **重要（业务方第二轮确认，B-6 / B-8）**：业务方**只能确认"样品信息项的内容与部件号清单有关系"，但无法确认生产部门实际就是照该清单填写的**（存在部门间沟通/习惯差异），并且**无法确认** `MONOC / BINOC / Rx` 等附加成分的准确含义——业务方唯一确切的信息来源就是那张表单照片。
>
> 由此产生一条贯穿全局的设计原则：
> **① 以表单上的原始输入为准（`sample_raw` 为事实来源）；② 部件号清单与附加成分只作为"尽力而为"的冗余参考，解析不到、对不上都不得阻断录入、不得作为验收条件。**
>
> （原业务方表述："把已有信息做好即可……有冗余更好，但没有也能跑。"）

因此设计为：
- **五个核心拆解字段**：**项目（M1/M2）必须纳入表单并作为结构化录入项**（B-7）；型号 / 规格 / 大小 / 左右尽量解析并允许人工修正。
- **冗余（扩展）字段** `MONOC/BINOC` 与 `Rx`：尽力解析填充，解析不到留空，**不参与任何校验，不作为验收条件**（B-8）。

核心五字段（结构化轨）：

| 层级 | 字段 | 示例值 | 字典/取值 | 要求 |
|---|---|---|---|---|
| 1 项目 | `sample_project` | `M2` | M1 / M2 | **必须纳入**（B-7） |
| 2 型号 | `sample_model` | `VID2` | VID1 Rx / VID2 | 尽量解析，可人工修正 |
| 3 规格 | `sample_spec` | `S2` | S1 / S2 | 尽量解析，可人工修正 |
| 4 大小 | `sample_size` | `SM` | MD / SM / LG | 尽量解析，可人工修正 |
| 5 左右 | `sample_side` | `R` | L / R | 尽量解析，可人工修正 |

冗余（扩展）字段（**均可空、不校验、不作为验收条件**）：

| 字段 | 示例值 | 说明 |
|---|---|---|
| `sample_class`（结构类别） | `MONOC` / `BINOC` / `MONOC_AND_BINOC` | 可多选（一个部件可能同时适用单目与双目）；**含义未确认** |
| `sample_is_rx`（处方镜） | `true` / `false` | 型号含 `Rx` / `RX` 时为 true；**含义未确认** |
| `sample_drawing_no`（匹配到的参考部件号） | `S2 - SM - R - VID2 - MONOC` | 来自 §4.2.3 参考清单，**仅供参考** |
| `sample_drawing_seq`（参考清单序号） | `09` | 便于按清单序号查询 |
| `sample_unmatched_reason` | `raw_only` / `no_drawing` / `partial` | 未匹配原因，驱动"待核对"清单 |

> 【保留的设计提醒】层级顺序与字符串书写顺序不一致：业务方描述的层级是 项目 → 型号 → 规格 → 大小 → 左右，而参考清单中部件号的**书写顺序**是 `规格 - 大小 - 左右 - 型号 - 结构类别`（如 `S1 - MD - R - VID2 - MONOC & BINOC`）。系统以**字段**为准，**解析器按 token 集合识别而非按位置解析**。

#### 4.2.4 解析与容错

| 编号 | 需求 |
|---|---|
| S-1 | 系统提供"样品信息解析器"：输入 `sample_raw` → 尽量输出 §4.2.2 各字段（**token 集合匹配，不依赖位置**） |

## 5. 表单提交的生命周期

### 5.1 数据组织原则（【确认】本次澄清）

> **每道工序都要填一份表单，但各工序所填内容不同（具体差异尚未确定）。**
> 每道工序的人在前端找到**自己工序对应的那张表单**，填写相关项并提交。

因此一个系统中的"表单提交"就是**一次工序填写**：

```
表单提交 Submission（form_no 唯一）
├─ 检验工序 operation_code        ← 表单第一列；也是检索/统计的主维度
├─ 检验总数 / 合格品 / 不合格品 / 合格率   ← 顶层栏目
├─ 样品信息 sample_raw（事实来源）+ 项目/型号/规格/大小/左右
├─ 单位、提交人（系统用户）、提交时间、保存次数
└─ 明细行 lines[]（1..N）
   └─ 不良缺陷明细：35 列 × 凹面/凸面/双面 = 105 个计数
```

**不再有"一张表单下多笔工序记录"的概念**（旧模型已废弃，见 §5.7）。

### 5.3 保存规则

| 编号 | 规则 |
|---|---|
| L-1 | `form_no` 唯一标识一次表单提交；不存在则创建（`save_count=1`），存在则**字段级合并**（`save_count+1`） |
| L-2 | **字段级合并**：请求里出现的字段才改；未出现的保持原值 |
| L-3 | **三态语义**：键不存在=不改；显式 `null`=清空；有值=写入。缺陷格子同样支持 `null`（清零该格子）；`defects` 给空对象 `{}` 表示清空全部缺陷计数 |
| L-4 | `lines` 一旦给出即**整笔替换**明细（不做行级合并；给 `[]` 表示清空明细） |
| L-5 | **表头与明细的优先级**：补丁里**显式给出**的表头栏目优先；未给出的按明细行重算 |
| L-6 | 合格率由服务端按 `合格品 / 检验总数 × 100` 计算（分母为 0 时为 null），除非调用方显式给出 |
| L-7 | 每次保存前把**保存前的完整内容**（提交 + 明细）写入历史快照，并写操作日志；历史**只增不可改** |
| L-8 | 并发：以 `save_count` 作乐观锁；不一致返回 `409` + 服务端当前内容 |
| L-9 | 未知字段 → **400**，并提示合法列清单 |
| L-10 | 允许保存**不完整**的内容（如只填了工序）；`is_complete=false` 并返回缺失清单 |
| L-11 | 记录**不做物理删除**；作废用 `state=VOID` + 原因，数据与历史保留 |
| L-12 | 批量提交（`forms` 数组）**整批一个事务**，任一失败则整批回滚 |
| L-13 | 无权限门槛：任何已登录用户都可读写（需求 B-14），但**必须留痕** |

### 5.4 完成度

| 需求 | 说明 |
|---|---|
| 最低判断依据 | 检验工序、单位、样品原始串、是否有明细行 |
| 输出 | `is_complete` + `missing_fields`（列名数组） |
| 未完成清单 | `GET /api/stats/incomplete-forms` 列出 `is_complete=false` 的表单 |
| 备注 | 各工序必填项未定，因此完成度只是**提示**，不阻断保存 |

### 5.5 状态取值（极简）

| 状态 | 说明 |
|---|---|
| `ACTIVE` | 已提交生效（唯一正常状态） |
| `VOID` | 已作废（逻辑标记 + 原因；数据与历史全部保留） |

### 5.6 幂等（弱网重试保护）

| 编号 | 需求 |
|---|---|
| I-1 | 写接口支持幂等键：请求头 `X-Idempotency-Key` 优先，其次请求体 `client_request_id` |
| I-2 | 同一用户、同一幂等键在 TTL（默认 24h）内重复提交 → **回放首次响应**，不重复写入 |
| I-3 | 同键但请求体不同 → `409`（避免误用） |
| I-4 | 失败响应（非 2xx）**不缓存**，允许用同一个键重试 |

### 5.7 与被取代模型的关系（历史说明）

| 方面 | 旧模型（已废弃） | 现行模型 |
|---|---|---|
| 核心实体 | 一张纸质表单 + 多笔工序记录 | **一次表单提交 = 某工序填的那张表单** |
| 工序位置 | 在"笔"上 | 在**提交**上（`operation_code`） |
| 明细缺陷列 | 5 类 × 3 面 = 15 个子项 | **35 列 × 3 面 = 105 个子列** |
| 表名 | `forms` / `form_records` / `record_lines` | `forms` / `form_lines` / `form_history` |

## 8. 验收标准（初稿，后端视角）

1. **一次填完**：按某工序的表单一次提交（工序 + 样品信息 + 明细含若干缺陷列），提交与明细完整落库，合格率与完成度由服务端算出。
2. **多次补填**：同一 `form_no` 第二次只提交部分栏目 → 未提交字段保持原值（含样品原始串），`save_count` 递增，历史快照与差异可查。
3. **三态语义**：键不存在=不改；`null`=清空该字段（缺陷格子清零）；缺陷 `{}`=清空全部缺陷计数。
4. **表头与明细优先级**：明细与表头同时给出时，显式给出的表头栏目不被明细覆盖。
5. **列目录**：`GET /api/form-fields` 返回 5 个顶层栏目 + 35 列 × 3 表面 = 105 个子列（含中文名与顺序）；新增一个缺陷列后无需改业务逻辑即可存取。
6. **工序表单**：`GET /api/form-templates` 返回各工序模板与列布局；**未登记的工序提交也能成功**（按通用模板）。
7. **字段校验**：未知列名 → 400 并提示合法列清单；计数为负/矛盾数据在 `enforce=strict` 下 422、默认 `warn` 下只警告并保存成功。
8. **检索**：按工序、样品各维度、单位、录入人、日期、完成度筛选与分页均正确（验证索引有效）。
9. **汇总**：按工序/样品维度分组的表单数、检验总数、合格品、不合格品、合格率正确；缺陷分布按 35 列 × 3 表面求和正确。
10. **幂等与并发**：同幂等键重复提交只写一次并回放首次响应；`expected_save_count` 不匹配返回 409；批量提交任一张失败则整批回滚。
11. **留痕**：每次保存均可追溯（操作人=系统用户、时间、前后内容）；作废后数据与明细仍可读。
12. **用户体系**：创建用户 → 停用后无法登录；除用户管理外不因缺少权限而被拒绝（B-14）。
13. 表单号并发生成 100 次无重号；同一提交下 `(form_id, seq)` 唯一。
14. 导出的 Excel/CSV 与查询结果一致（**导出接口尚未实现**）。

| **Q19** | 多工序的落库形态（每工序一行 vs 分次补齐同一组栏目）？ | **已确认：不做确认，要求最大灵活性**（B-16） | **笔与行都保留工序字段**，不校验一致性，不收敛（§5.1） |
| **Q20** | 系统最终用在哪个环节（工序现场 / 集中录入）？ | **已确认：无法确认，按最大灵活性设计**（B-16） | 两种节奏都必须能跑 → 校验默认不阻断、不假设使用环节（§4.1.5、§5.2） |
| **Q21** | 汇总统计的具体口径（按笔去重？导出格式？） | **待确认**，但已确认**需要**该功能，且**本期不实现**（B-18） | 本期只保证样品信息各维度与计数在库中可直接查询（§4.7） |
