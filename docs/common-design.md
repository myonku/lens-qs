# 公共设计约定

版本：2.0.0；文档修订：2026-11-05。本文与[领域设计](design.md)、[API 契约](api.md)共同构成正式设计基线。本文规定跨模块的原则与约束；业务身份、生命周期和统计资格以领域设计为准，线上字段以 API 契约为准。设计要求不等于已经通过实现或部署验收，尚需独立验证的项目见第 10 节。

## 1. 工程与分层

采用 Go 1.26+、Gin、database/sql + sqlx 的模块化单体，单一仓库管理 `docs/` 与 `backend/`，不建立嵌套 Git 仓库。交付范围为后端；现场分次录入与集中录入共用同一套模型、校验和 API，不通过不同调用场景创建不同事实来源。

| 层/模块 | 职责 | 边界 |
|---|---|---|
| HTTP 与中间件 | 认证、管理员入口保护、请求解析、响应、CORS、请求关联 | 不在 handler 内另写一套业务规则 |
| auth / users | 密码、会话、账户启停和管理 | 系统操作者来自可信身份，不取自纸面人名 |
| dictionary / sample | 字典、单位、参考部件号、辅助解析及人工确认缓存 | 不判断检验单是否正式、不替代产品批身份 |
| ledger | 身份、占用、版本、授权、发布取消、统计与报告 | 同一规则在单笔和批量、两种数据库中一致 |
| store / database | 连接、方言适配、事务、迁移与统一时间 | SQL 参数化；字段和分组表达式必须由白名单映射 |

数据库支持 SQLite（开发与单机）和 PostgreSQL。两套手写 SQL 迁移随二进制发布，按序执行；已发布迁移不改写。驱动占位符由 Rebind 等方言适配处理。双库的空值、布尔、日期、约束和事务语义须保持一致，不能只以一种数据库通过作为双库结论。

资源 ID 是不透明稳定字符串，客户端不得拆解其前缀、时间或流水作为业务含义；共享号、批号、工序编码和资源 ID 分开。服务启动应在连接/迁移失败时明确失败，退出应停止接收新请求、等待在途事务有界结束并关闭数据库；不能在终止时留下已返回成功但未提交的写入。

## 2. 认证、会话与权限

密码采用 Argon2id、PHC 自描述格式，禁止明文存储、回显或记录日志。会话使用高熵随机令牌，数据库只存令牌 SHA-256 哈希；支持服务端撤销，不以客户端自行删除令牌代替撤销。

认证支持 HttpOnly Cookie 与 `Authorization: Bearer <token>`。Cookie 默认名 `sid`，Path=/，SameSite=Lax；HTTPS 部署启用 Secure。浏览器 Cookie 调用必须携带凭据；跨站部署须核对 SameSite，不能仅配置 CORS 就认定 Cookie 可用。Bearer 令牌具有会话同等权限，按凭据保护。

| 配置 | 默认 | 语义 |
|---|---|---|
| SESSION_TTL | 12h | 会话绝对有效期 |
| SESSION_IDLE_TTL | 2h | 空闲失效窗口；活动不能突破绝对到期 |
| MAX_LOGIN_FAIL | 5 | 连续登录失败上限 |
| LOCK_DURATION | 10m | 达到失败上限后的账户锁定时间 |
| COOKIE_NAME | sid | Cookie 名 |
| COOKIE_SECURE | false | 本地 HTTP 可用；HTTPS 部署设为 true |

退出撤销当前会话；本人改密、管理员重置密码或停用账户须使其已有会话失效。账户类型变更还须同事务清除此用户的业务幂等结果。会话失效后重新登录，接口不得通过残留 token 放行业务。初始管理员仅在用户库为空时引导，重启、迁移和种子初始化不得覆盖已有密码。

权限有两个独立维度：`is_admin` 管理账户；`account_type` 限制填报类型。字典、解析、业务读取与统计需登录；共享字典维护不因填报类型被划成两个副本。业务写授权集中判定，普通与管理员都只能写本账户类型；同类型不按创建者限制更正。后续扩展授权应替换集中判定，不在端点内散布例外。

首次强制改密、独立 IP 限流、外部身份提供方不能仅凭字段、配置或设计文字认定已交付，见第 10 节。

## 3. 字典与参考资料

字典项以 `category + code` 标识，保留稳定 ID；`label` 是显示文字，`sort_no` 控制排序，`active` 控制可选性，`meta` 可存解析别名等扩展资料。单位使用独立目录，`code/name` 与 ID 分开。停用不是删除，不得改写历史快照中当时的纸面文字和内容。

样品核心维度为项目、型号、规格、大小、左右；解析匹配可使用 code 和别名。工序身份引用字典 ID；模板决定展示范围，不凭一个临时中文名称偷偷生成业务工序。

参考部件号是辅助清单，不是准入目录。清单无匹配、结构类别未知、附加成分含义不明均不能阻止草稿保存或要求改写原文。字典和参考资料更新不批量回填历史检验版本。

可配置范围须明确：字典项、标签、排序和解析别名可维护；增加一个真实持久化字段、缺陷类别或改变统计含义仍需字段目录、结构/迁移、校验与契约共同变更，不能承诺只改字典即可完成。

调用方可缓存目录，但必须有更新/失效策略，不能永久保存停用项作为可选值。服务端若提供version/ETag，应以实际响应协商；当前未核验该协议，不声明所有目录都有版本头。模板版本不能拿来代替字典版本。

## 4. 样品双轨与解析缓存

`sample_raw` 保存录入原文；结构化核心五项用于检索、分组和辅助展示。解析、参考匹配、人工确认结构化字段都不得反向改写原文。调用方显式纠正某单原文时通过内容修订留痕；这与解析器自动改写不同。产品批身份与单据内容独立，修改内容的五项不改变产品批归属。

解析采用位置无关的 token 集合匹配。归一化只用于匹配/缓存键，不覆盖原始字符串；处理大小写、全半角、分隔符与字典别名，保留组合语义。业务层级“项目→型号→规格→大小→左右”不等于输入串的位置。未知 token 原样进入辅助结果，不猜测 `ND2` 必然为 `VID2`。

解析结果携带已识别项、unknown_tokens、confidence、匹配结果和说明。`raw_only/partial/no_drawing` 表示不同程度的不确定性，不是保存失败；置信度也不是质量合格率。class/is_rx/drawing 等参考属性可以未知，不升级成检验内容的必填字段。

| 动作 | 作用 | 不产生的副作用 |
|---|---|---|
| parse | 尽力解析，可读取/复用缓存 | 不创建、发布或修改检验单 |
| confirm | 按原始串记录人工结构化确认到缓存 | 不改原文、不追溯更新已保存版本 |
| cache 查询 | 展示规范化键、token 和命中信息 | 不表示已核验生产批身份 |

解析缓存是可重建辅助资料，内容版本是业务证据。两者不得互相替代；缓存失效或字典变化不改变既有正式结果。是否缓存某次自动解析、缓存刷新和具体置信度算法属于实现策略，不能将 parse 描述成“保证完全无持久化副作用”。

## 5. 字段目录、模板与保存

字段目录统一提供编码、中文标签、类型、可空/只读、缺陷及表面顺序、时间格式。前端渲染、输入白名单、存储和统计映射须一致。缺陷采用 35 类 × 3 表面，表面顺序为 concave、convex、both；显示标签变化不改变编码含义。

纸面单位、送检人/时间、检验人/时间、操机员、交接员七个栏目全部保留。“七栏目”不是 API 字段数量：单位有 ID/原文，时间按精度使用日期或时点；工序是组身份，良率是只读计算值，不能把展示栏目总数称为可写字段总数。

模板带 `template_version`，与保存版本一起留存。当前工序模板共用完整栏目，不因工序名称预设业务必填集合。没有专用布局可使用通用布局，但不免除工序 ID 的有效性校验。NORMAL/SAMPLING 共用模板，权限由账户和组类型决定。

内容补丁实行三态：不传保持、null 清为未知、有值写入。对象递归合并；数组提交时完整替换，[] 清空，null 拒绝。行/变化条目不是可独立 PATCH 的资源，不按 seq 或旧 ID 合并。明确零与未知不同。只读派生量不得作为输入覆盖；counts 是正式计数源，line_totals 和 declared_differences 只用于核对。

保存追加完整内容快照，发布指定草稿才改变正式资格。无审批并不等于保存即入正式统计。草稿、完整度、校验问题、正式状态是独立概念，调用方不得互相代用。

### 5.1 日期只保留规范值

日期输入使用前端日期/时间选择组件，不接收自由文字。后端独立解析与校验后，仅保存规范日期YYYY-MM-DD或带时区时点规范化后的UTC秒精度值，不另存输入日期原文，不提供日期原文的写入/响应字段。使用TEXT物理列不代表允许任意格式。

同一事件按实际精度选择*_date或*_at，二者最多一个非空；未知为null，不补造零点。业务日由规范日期直接取得，或由规范时点按Asia/Shanghai派生。列表、报告、统计与筛选共用该口径，不从原文解析补值，也不用系统创建时间兜底。数量变化的occurred_date/occurred_at同样适用；系统时间由服务端生成。

本约定仅取消日期原文轨道，sample_raw、单位原文和人员文字继续保留。正式内容中的日期更正仍须追加版本，不覆盖历史。本项已确认设计，代码、字段目录与存量结构须后续适配，文档更新不表示数据库已经变更。

## 6. 校验与完整度

规则在服务端集中实现，前端可提前提示，不能豁免服务端约束。错误应含可读中文信息及可定位字段；调用方按 code、reason 分支，不能依赖 message 文案解析。匹配失败的辅助提示来自解析结果，不保证都转换成保存响应里的 issues。

| 层次 | 处理 |
|---|---|
| 协议 | 未知字段、类型错误、缺控制字段：400 |
| 身份与权限 | 未认证401、跨类型或非管理员管理用户403 |
| 状态与并发 | 重复占用、版本/生命周期冲突：409 |
| 规范数据 | 负数、非法日期/枚举等：按 API 的400/422边界拒绝 |
| 资料不足或核对差异 | 缺纸面栏目、未知数量、计数/声明/明细差异：提示并保留未知 |
| 存储 | 事务失败不放行业务；有界等待耗尽按503处理 |

不把“非负整数”降成可忽略警告；也不把“还没填完”升级成普遍禁止保存。发布另须满足归组及规范数据约束，普通未知计数允许发布并标示不完整。

`is_complete/missing_fields` 表示当前内容的资料完整度，不表示审核、无数量矛盾或可计算良率。不得用系统操作者补纸面检验人，也不得用创建时间补纸面检验日。完整度具体字段清单尚缺可据以确定的统一 v2 文档定义，列入第 10 节；不能直接复制任何早期五项或七项判据冒充当前行为。

## 7. 请求、并发与留痕

HTTP JSON 字段使用 snake_case；成功/失败包装及分页以 API 为准，根信息和健康检查独立。请求关联 ID 用于排障，与业务幂等键无关。日志不得记录密码、完整会话令牌或未经脱敏的请求体。

检验业务的幂等结果、对象版本、占用、审计同事务；失败全部回滚。共享用户/字典/解析写入不自动继承业务幂等协议，也不保证与 ledger 相同的 PATCH 空值规则。调用方遇到版本冲突重新读取并核对，不盲目以当前 version 重放旧意图。

每次成功内容保存及发布、取消、关组/开放等状态动作保留可信操作者、系统 UTC 时间和变更原因；业务审计保留 before/after，历史版本用于内容差异，事件序号用于历史状态回放。IP/User-Agent 等只作排障信息，不作为授权身份。审计和业务历史不提供普通修改/物理删除接口。

账户/字典维护、登录失败与会话撤销也有审计价值，应记录最小必要的动作和结果；它们是否已全面覆盖须独立核验，不能因业务存在 audit_logs 就假定全局拦截器已经审计所有请求。只采集必要的姓名、工号等人员资料，不因排障额外留存完整凭据或无关个人信息。

应用层追加写与数据库层防篡改不是同一个保证。独立数据库权限、外部备份或其他防篡改机制未经验收，不得声称管理员也无法篡改。测试清理属于停写维护动作，保留账户字典、清理证据并重建历史起点；不作为普通质量记录删除入口。

## 8. 部署、安全与恢复

内网单机可用 SQLite，API + PostgreSQL 可通过 Compose 部署。TLS 在反向代理终止，配置可信代理与来源；生产启用 HTTPS 和 Secure Cookie。CORS 按明确来源配置，留空不下发 CORS 头；带 Cookie 的浏览器调用必须验证预检、凭据与响应可读性。CORS 不能代替认证、授权或 CSRF 风险评估。

运行配置与凭据不进仓库、镜像或文档示例。镜像只含程序、迁移和必要参考 CSV；数据库、.env、备份均外置。迁移和种子执行应可重复，不覆盖已有账户密码；健康检查不能代替迁移完整性和业务验收。

SQLite 使用 backup API 或停写后的完整一致备份，不能在写入中只复制主文件而忽略 WAL；PostgreSQL 使用 pg_dump，按环境确定增量/WAL 策略。每日备份、备份保留30天是运维基线，实施情况须验收；加密、异地副本与RPO/RTO须在部署时明确。质量内容与操作日志不随备份到期删除；保留期限按业务及合规要求确认，未确认前不执行自动清理。恢复演练必须验证账户、字典、版本、审计、外键及历史起点。结构降级不能恢复被删除的数据；已有新写入时先保全新数据再制定恢复方案。

## 9. 性能与验证设计

目标规模为数十人并发、年 10^4–10^5 笔量级；单笔写入 P95 <500ms、千笔量级条件查询 P95 <2s 是待实测目标，不是已取得的服务保证。测试记录须标明硬件、数据库、并发、数据量、版本数和样本分布。

按身份唯一键、组/批号占用、版本归属、查询日期/工序建立索引；列表分页、历史按需载入。统计先选正式版本集合，再分别聚合计数/缺陷/变化，防 JOIN 乘倍。历史回放与大范围报告应单独测成本，不能沿用普通列表耗时。当前写闸门串行化业务写入，多开 API 实例不承诺线性写扩展。

验证覆盖补丁三态、未知与零、数组替换、解析不改原文、缓存确认不改历史、账户会话撤销、类型权限、并发占用、事务失败回滚、双库升级与恢复。安全、性能、部署演练各自留证，不能用单元测试或文档检查代替。导出下载、外部身份接入和多实例扩展未列为当前交付能力。

## 10. 尚需独立核验的设计事项

以下事项缺乏统一可验证的实现/部署说明，保留为明确待核验项。规范性设计要求继续有效，实际状态需单独核验；不能仅凭本文认定已经交付。

| 项目 | 需形成的结论/验收 |
|---|---|
| 完整度字段清单 | 确定 v2 missing_fields 的精确键、条件与顺序，同步 API 和调用方验收；不得以补齐文档名义新设发布门槛 |
| 共享接口分页及输入规则 | 核验用户列表 page_size 上限/非法值处理，字典/用户 PATCH 的 null 语义、目录限制及省略字段；不套用 ledger 规则 |
| 认证安全 | 密码强度/Argon2id参数、令牌冲突时的取用顺序、重置/停用撤销、must_change_pwd 是否真正限制访问、按IP限流范围 |
| 请求关联与代理 | 核验请求 ID 响应头、可接受来源、CORS 自定义头及可信代理，确保日志可关联且不会信任伪造身份 |
| 目录缓存与共享审计 | 核验目录version/ETag及更新失效策略；确认用户/字典变更和登录/会话事件的实际留痕范围 |
| 证据保护与恢复 | 核验部署账户的数据库权限、备份频率/留存/加密、恢复演练及其历史回放一致性 |
| 非功能目标 | 在目标环境测量 P95、历史回放和大范围报告；确定超时/资源上限，避免无限读取 |

完成这些核验须以单独实现/部署验收结果更新正式契约，不以本次文档修订推定通过。
